# 礼金往来记录网站实施计划

**已锁定的关键默认值：** 删除有礼金关联的亲戚或宴请时禁止删除；六种宴请类型采用全局系统字典；`gift_type=礼品` 的 `amount` 也必须大于 0。

## 2. 实施阶段拆分

**阶段 1：项目地基与数据库**
- 目标：完成目录、自动加载、单入口路由、PDO 连接、建表种子数据和基础布局。
- 涉及文件：`public/`、`config/`、`app/Core/`、`database/schema.sql`、`database/seed.sql`、`README.md`。
- 完成标准：空库可成功执行 `schema.sql`、`seed.sql`；所有 PHP 文件通过 `php -l`；`/login` 正常返回页面；未定义路由返回 404；数据库连接失败返回友好错误且不泄露配置。此阶段结束后应用可启动。

**阶段 2：注册、登录与安全会话**
- 目标：注册、登录、退出、修改密码，CSRF 和登录守卫。
- 涉及文件：`AuthController`、`AuthService`、`UserDao`、`Session`、`Csrf`、`Auth`、`Flash`、`Validator`、认证视图、布局和路由。
- 完成标准：注册唯一用户名；密码使用 `password_hash`/BCrypt 且不回显；登录成功重新生成 session；未登录访问业务页跳转登录；无 token 或错误 token 的 POST 被拒绝；退出和改密后会话失效；浏览器验证登录态。此阶段结束后应用可运行并完成认证闭环。

**阶段 3：亲戚 CRUD**
- 目标：亲戚列表、筛选、创建、编辑、软删除，完整用户隔离。
- 涉及文件：`RelativeController`、`RelativeService`、`RelativeDao`、亲戚视图、路由。
- 完成标准：列表可按姓名/关系关键字及 `family_side`、`category` 筛选；编辑和删除仅命中当前用户的未删除记录；越权访问其他用户 ID 返回 404；删除后列表和后续查询均排除该亲戚。此阶段结束后应用可运行。

**阶段 4：宴请 CRUD**
- 目标：系统类型只读展示，自己办/亲戚办宴请的创建、查询、编辑、软删除。
- 涉及文件：`BanquetController`、`BanquetService`、`BanquetDao`、`BanquetTypeDao`、宴请视图、路由。
- 完成标准：系统六种类型按 `sort` 显示且不可改；自己办时 `host_relative_id` 为空且不提交；亲戚办时必须选择当前用户自己的亲戚；类型、主办类型、日期范围筛选正确；删除和越权规则与亲戚模块一致。此阶段结束后应用可运行。

**阶段 5：礼金明细 CRUD**
- 目标：收/送、金额、类型、日期、备注的增删改，以及方向与宴请主办类型的一致性校验。
- 涉及文件：`GiftRecordController`、`GiftRecordService`、`GiftRecordDao`、礼金视图、路由、金额校验器。
- 完成标准：只能选择当前用户自己的亲戚和宴请；自己办强制“收”，亲戚办强制“送”，且亲戚办时礼金亲戚必须等于宴请主办亲戚；金额以字符串校验并写入 DECIMAL，不使用浮点；礼金列表支持方向、亲戚、宴请类型、日期区间筛选；软删除正确。此阶段结束后应用可运行。

**阶段 6：首页看板与统计**
- 目标：总收、总支、净额、Top 亲戚，以及按类型/时间/亲戚/方向的统计页面。
- 涉及文件：`DashboardController`、`StatisticsController`、`StatisticsService`、`StatisticsDao`、看板和统计视图、核心统计 SQL。
- 完成标准：看板汇总值与明细手工核对一致；无数据时显示 `0.00`；Top 亲戚按净额绝对值降序；统计页筛选组合正确，结果不跨用户。此阶段结束后应用可运行并完成 MVP 功能。

**阶段 7：集成验收与部署检查**
- 目标：完整手工验收、安全清单、Apache/Nginx 启动和重装流程检查。
- 涉及文件：README、服务器配置示例、schema/seed、全部模块。
- 完成标准：完成两个测试用户的全流程回归，确认数据隔离；重新执行空库初始化可复现系统字典；Apache/Nginx 单入口访问正常；POST 删除/提交均有 CSRF；确认无明文密码、无 SQL 拼接、无浮点金额。此阶段结束后可交付。

## 3. 建表要点

**建表顺序**

1. `users`
2. `relatives`
3. `banquet_types`
4. `banquets`
5. `gift_records`

统一使用 InnoDB、`utf8mb4`、`BIGINT UNSIGNED` 主键、`created_at`/`updated_at DATETIME`、`is_deleted TINYINT(1) NOT NULL DEFAULT 0`。`banquet_date` 和 `gift_date` 使用 `DATE`，不做时间点记录。

**索引与外键策略**

- `users.username` 唯一；`status` 默认 `1`。
- `relatives`：`(user_id,is_deleted,name)`、`(user_id,is_deleted,family_side)`，并为组合外键增加唯一索引 `(user_id,id)`。
- `banquets`：`(user_id,is_deleted,banquet_date)`、`(user_id,type_id,is_deleted)`，并增加唯一索引 `(user_id,id)`。
- `gift_records`：`(user_id,is_deleted,gift_date)`、`(user_id,relative_id,is_deleted)`、`(banquet_id,is_deleted)`、`(user_id,direction,is_deleted)`。
- 外键使用 `ON DELETE RESTRICT`，不使用级联删除。软删除记录仍保留外键，物理删除只会在明确的数据维护操作中发生。
- 为阻止跨用户关联，`gift_records (user_id,relative_id)` 引用 `relatives (user_id,id)`，`gift_records (user_id,banquet_id)` 引用 `banquets (user_id,id)`，`banquets (user_id,host_relative_id)` 引用 `relatives (user_id,id)`。外键是最后防线，Service 仍必须校验当前用户归属。

**字典初始化**

`seed.sql` 写入六条系统宴请类型，`user_id=NULL`、`is_system=1`：结婚、生子、满月周岁、乔迁、升学、其他，`sort` 分别为 1 至 6。种子脚本应可重复执行，不重复插入。系统类型只读，不提供自定义类型入口。

**对上表的调整建议**

- 【建议调整】`banquet_types.user_id` 设为可空，系统类型的 `user_id=NULL`。原因是六种类型是全局只读字典；未来扩展用户自定义类型时，再写入真实 `user_id`，查询使用“系统类型或本人类型”。
- 【建议调整】`banquets.host_relative_id` 设为可空，自己办时为 `NULL`，亲戚办时必填。原因是自己办的宴请没有主办亲戚。
- 【建议调整】增加 MySQL 8 `CHECK`：`status IN(0,1)`、`direction IN(1,2)`、`gift_type IN(1,2,3)`、`host_type IN(1,2)`、`amount > 0`。用于数据库层兜底枚举和金额约束。
- 【建议调整】将 `banquet_date`、`gift_date` 明确为 `DATE`，避免日期时间时区和边界歧义。

## 4. 核心业务规则清单

**用户隔离与越权防护**

- 所有业务 DAO 查询必须包含 `user_id = :current_user_id`；按 ID 查询时必须同时携带 `user_id`。
- `user_id` 只从登录会话获取，禁止从表单、GET 参数或客户端传入。
- 访问、编辑、删除他人的资源统一返回 404，避免枚举其他用户数据。
- `host_relative_id`、`gift_records.relative_id`、`gift_records.banquet_id` 在 Service 层必须验证属于当前用户。
- 系统宴请类型为唯一共享字典，只读；业务数据仍按用户完全隔离。

**收送方向与宴请类型一致性**

- `host_type=1` 自己办，礼金方向只能为 `direction=1` 收。
- `host_type=2` 亲戚办，礼金方向只能为 `direction=2` 送。
- 亲戚办时，`banquets.host_relative_id` 必填；该宴请下的礼金 `relative_id` 必须等于 `host_relative_id`。
- 自己办时，`host_relative_id` 必须为空，礼金 `relative_id` 为送礼亲戚。
- 已存在未删除礼金时，禁止修改宴请的 `host_type` 或 `host_relative_id`，避免历史流水口径漂移。

**删除与软删除**

- 所有列表、统计和看板查询只读取 `is_deleted=0`。
- 礼金明细可以软删除。
- 亲戚存在未删除礼金，或仍被未删除的亲戚办宴请引用时，禁止删除亲戚。
- 宴请存在未删除礼金时，禁止删除宴请。
- 不执行连带软删除，删除前必须由用户先处理关联明细；提示中显示未删除关联条数。

**金额规则**

- 金额输入使用字符串校验：正整数或最多两位小数，必须大于 0，且不超过 `DECIMAL(10,2)` 的最大值。
- PHP 比较和运算使用 BCMath 或字符串比较，不经过 `float`。
- 数据库读取金额保持字符串，禁止使用浮点类型参与计算。

**字段校验**

- 用户名：3 至 30 位字母、数字或下划线，用户名唯一。
- 密码：8 至 72 字节，使用 BCrypt；修改密码必须验证原密码。
- 昵称、电话、邮箱：电话和邮箱可选，不验证真实性，也不要求唯一。
- 亲戚：`name` 必填，`relation` 为短文本，`family_side` 取父方/母方/配偶方/其他，`category` 取长辈/平辈/晚辈/其他，`gender` 取男/女/未填。
- 宴请：`type_id`、`host_type`、`title`、`banquet_date` 必填。
- 礼金：`banquet_id`、`relative_id`、`direction`、`amount`、`gift_type`、`gift_date` 必填；`gift_type=礼品` 时 `gift_desc` 必填，其余类型备注可选。

**会话与安全**

- Session cookie 使用 `HttpOnly`、`SameSite=Lax`，生产环境启用 `Secure`。
- 登录成功和修改密码成功后重新生成 session ID；退出时销毁会话。
- 所有 POST 表单携带 session 级 CSRF token，任何写操作先校验。
- 所有页面输出通过 `htmlspecialchars` 转义；所有 SQL 使用 PDO 预处理语句。
- 涉及多表关联的写操作使用数据库事务；当前 MVP 不引入登录限流和审计日志。

## 6. 四条核心 SQL

**1. 按亲戚统计收、送和净额**

```sql
SELECT r.id, r.name,
       COALESCE(SUM(CASE WHEN g.direction = 1 THEN g.amount ELSE 0 END), 0) AS total_received,
       COALESCE(SUM(CASE WHEN g.direction = 2 THEN g.amount ELSE 0 END), 0) AS total_sent,
       COALESCE(SUM(CASE WHEN g.direction = 1 THEN g.amount ELSE -g.amount END), 0) AS net
FROM relatives r
LEFT JOIN gift_records g
       ON g.user_id = :user_id
      AND g.relative_id = r.id
      AND g.is_deleted = 0
WHERE r.user_id = :user_id
  AND r.is_deleted = 0
GROUP BY r.id, r.name
ORDER BY net DESC, r.name;
```

**2. 按宴请类型和时间区间汇总**

```sql
SELECT t.id, t.code, t.name,
       COUNT(g.id) AS record_count,
       COALESCE(SUM(CASE WHEN g.direction = 1 THEN g.amount ELSE 0 END), 0) AS total_received,
       COALESCE(SUM(CASE WHEN g.direction = 2 THEN g.amount ELSE 0 END), 0) AS total_sent
FROM gift_records g
JOIN banquets b
       ON b.id = g.banquet_id
      AND b.user_id = :user_id
      AND b.is_deleted = 0
JOIN banquet_types t ON t.id = b.type_id
WHERE g.user_id = :user_id
  AND g.is_deleted = 0
  AND g.gift_date BETWEEN :date_from AND :date_to
GROUP BY t.id, t.code, t.name, t.sort
ORDER BY t.sort, t.id;
```

**3. 时间区间礼金流水**

```sql
SELECT g.id, g.direction, g.amount, g.gift_type, g.gift_desc, g.gift_date, g.remark,
       r.id AS relative_id, r.name AS relative_name,
       b.id AS banquet_id, b.title AS banquet_title, b.host_type,
       t.name AS banquet_type_name
FROM gift_records g
JOIN relatives r
       ON r.id = g.relative_id
      AND r.user_id = :user_id
      AND r.is_deleted = 0
JOIN banquets b
       ON b.id = g.banquet_id
      AND b.user_id = :user_id
      AND b.is_deleted = 0
JOIN banquet_types t ON t.id = b.type_id
WHERE g.user_id = :user_id
  AND g.is_deleted = 0
  AND (:direction IS NULL OR g.direction = :direction)
  AND (:relative_id IS NULL OR g.relative_id = :relative_id)
  AND (:banquet_id IS NULL OR g.banquet_id = :banquet_id)
  AND g.gift_date BETWEEN :date_from AND :date_to
ORDER BY g.gift_date DESC, g.id DESC
LIMIT :limit OFFSET :offset;
```

**4. 首页看板汇总与 Top 亲戚**

```sql
SELECT COALESCE(SUM(CASE WHEN direction = 1 THEN amount ELSE 0 END), 0) AS total_received,
       COALESCE(SUM(CASE WHEN direction = 2 THEN amount ELSE 0 END), 0) AS total_sent,
       COALESCE(SUM(CASE WHEN direction = 1 THEN amount ELSE -amount END), 0) AS net
FROM gift_records
WHERE user_id = :user_id
  AND is_deleted = 0;
```

```sql
SELECT r.id, r.name,
       COALESCE(SUM(CASE WHEN g.direction = 1 THEN g.amount ELSE -g.amount END), 0) AS net
FROM gift_records g
JOIN relatives r
       ON r.id = g.relative_id
      AND r.user_id = :user_id
      AND r.is_deleted = 0
WHERE g.user_id = :user_id
  AND g.is_deleted = 0
GROUP BY r.id, r.name
ORDER BY ABS(net) DESC, r.name
LIMIT :limit;
```

## 7. 待确认项与默认建议

1. **统计时间口径**：默认按 `gift_date` 统计流水，不使用 `banquet_date`；统计页明确展示“流水日期”。
2. **Top 亲戚口径**：默认按净额绝对值降序，取前 10 条，同时显示收、送和正负净额。
3. **亲戚筛选字典**：默认 `family_side=父方/母方/配偶方/其他`，`category=长辈/平辈/晚辈/其他`，`gender=男/女/未填`，`relation` 使用短文本输入。
4. **日期精度**：默认 `DATE`，不记录小时分钟；后续需要精确时刻时再单独扩展。
5. **电话与邮箱**：默认不要求唯一，也不做真实性验证；用户名保持唯一。
6. **金额显示**：默认人民币格式，始终显示两位小数，如 `¥1,200.00`；数据库仍以 DECIMAL 存储。
7. **登录限流**：默认 MVP 不加入登录失败限流、验证码或账号冻结。
8. **运行环境**：当前主机 PATH 中未检出 `php` 和 `mysql`，阶段 1 前需安装或启用 PHP 8.1+、MySQL 8，并将 `public/` 配置为 Web 根目录；本地默认同时提供 Apache 和 Nginx 示例。
